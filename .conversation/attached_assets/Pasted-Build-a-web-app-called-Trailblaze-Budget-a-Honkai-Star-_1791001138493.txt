Build a web app called "Trailblaze Budget": a Honkai: Star Rail lineup
builder for free-to-play players who are missing meta characters.

PROBLEM
Guides only show the ideal team. F2P players own a DPS but often lack the
meta sub-DPS, support, or sustain. This app shows the meta lineups for a DPS,
then rebuilds them around what the player actually owns and explains the
trade-off.

CORE FLOW
Step 1. User picks ONE DPS they own. App shows up to 5 recommended lineups
        for that DPS, ranked, with the ideal meta teammates.
Step 2. For any recommended teammate the user does not own, they tap
        "Don't have". App asks which characters of that role (sub-DPS,
        support, or sustain) they do own, then substitutes the best one and
        re-ranks the lineups.

STACK
- Frontend: React + Vite + TypeScript + Tailwind
- Backend: Node + Express + TypeScript
- Database: the built-in Replit PostgreSQL
- LLM: API key stored in Replit Secrets (LLM_API_KEY)
- No login. Identify users with an anonymous ID stored in localStorage.

GAME DATA SYNC
- Do not hardcode the character list. On server start, and via a "Sync game
  data" button on /admin, fetch characters.json, paths.json, elements.json
  from https://raw.githubusercontent.com/Mar-7th/StarRailRes/master/index_min/en/
  and cache them in the database. If the fetch fails, use the cached copy.
- Translate internal keys with paths.json and elements.json (for example
  Knight = Preservation, Thunder = Lightning). Never show internal keys.
- Entries named "{NICKNAME}" are Trailblazer variants. Rename to
  "Trailblazer (<path>)" and merge the male and female pair of each path.
- Icons: https://raw.githubusercontent.com/Mar-7th/StarRailRes/master/<icon>
- Startup self-check: log a warning if character id 1503 (Pearl) is missing.

CURATED DATA (mine, stored separately so a sync never overwrites it)
1. character_meta: character_id, roles[] (dps, sub_dps, support, sustain),
   generic_score (0-100), is_released (default false for new characters).
   NEVER derive roles from path. Example: Pearl is path Elation but her role
   is sustain.
2. lineups: dps_id, rank (1-5), title, slots[3]. Each slot: role
   (sub_dps | support | sustain) and character_id. A DPS may have fewer than
   5 lineups. Never pad with invented ones.
3. substitutes: dps_id, role, options[]. Each option: character_id,
   score (0-100), loss_note (what the team loses versus the meta pick),
   fix_note (how to compensate).
Do not invent kits, roles, lineups, or rankings from your own knowledge.
Create the schema plus ONE DPS with sample data clearly marked "SAMPLE".
I will enter the real data through /admin.

OWNERSHIP MODEL
Per anonymous user, store a map of character_id to "owned" or "not_owned".
Anything not in the map is "unknown". The picked DPS is saved as owned.
Ownership is global: it applies to every lineup and every future DPS.

LINEUP ENGINE (pure function, no LLM, unit tested)
Input: dpsId and the ownership map. For each curated lineup of that DPS:
- Slot character is owned or unknown: keep it. Mark unknown as unconfirmed.
- Slot character is not_owned: replace with the highest-score option from
  substitutes(dpsId, role) that is owned and not already in this team.
- No owned option in that pool: fall back to the owned character with a
  matching role and highest generic_score, and flag the slot "weak".
- Nothing owned for that role at all: leave the slot "needs input".
- Slot score: 100 for the original pick, the option's score for a
  substitute, generic_score / 2 for a weak fallback, 0 for needs input.
- Lineup completeness = average slot score.
After resolving, remove lineups that became identical, then sort by
completeness. Return for each slot: meta pick, final pick, status,
loss_note, fix_note.

LLM EXPLAINER (on demand only, via an "Explain this team" button)
Send the resolved lineup JSON and ask for a short explanation: why the team
works, what is lost versus the meta version, how to play around it. System
prompt: use only the JSON provided, never add characters or mechanics that
are not in the input. If the call fails, the card still shows loss_note and
fix_note.

API
GET  /api/dps                          released DPS that have lineups
GET  /api/lineups/:dpsId?anonId=       resolved lineups
GET  /api/substitutes/:dpsId/:role     candidate list for the picker
PUT  /api/ownership/:anonId            { characterId: status, ... }
POST /api/explain                      { lineup }
/api/admin/*                           sync, character_meta, lineups,
                                       substitutes

SCREENS
1. Pick DPS: icon grid of DPS only, with search and element filter.
2. Lineups: up to 5 ranked cards. Each card shows 4 character icons with
   role labels and a completeness bar. Each teammate has two buttons:
   "Have" and "Don't have".
3. Substitute sheet (opens on "Don't have"): "Which <role> do you own?"
   Shows the substitute pool for that DPS and role as multi-select chips,
   ordered by score. On confirm, ticked ones are saved as owned and unticked
   ones as not_owned, then all lineups refresh.
4. A substituted slot shows the meta pick greyed out with an arrow to the
   user's pick, plus loss_note and fix_note underneath.
5. /admin: sync status (last sync time, character count, 10 highest IDs),
   a "Needs review" list of characters without roles or not released, and
   editors for lineups and substitutes.
Characters with is_released = false or empty roles never appear to users.
